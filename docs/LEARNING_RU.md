# Как изучать SeatBook

Проект развивает идеи из твоих `house-service` и `jobqueue`: знакомые HTTP, PostgreSQL, роли и фоновые процессы теперь связаны правилами бронирования.

## Порядок чтения

1. `internal/store/schema.sql`: объясни каждую таблицу, внешний ключ и частичный уникальный индекс.
2. `cmd/api/main.go`: проследи запуск, остановку и работу фонового процесса.
3. `internal/httpapi/api.go`: пройди регистрацию, вход и middleware авторизации.
4. `internal/store/store.go`, метод `Reserve`: проследи транзакцию от ключа идемпотентности до `Commit`.
5. Там же `Transition` и `Expire`: сравни порядок блокировок.
6. `internal/httpapi/api_test.go`: запусти конкурентные тесты и объясни ожидаемые HTTP-коды.
7. `web/app.js`: проследи путь от выбора места до API и отображения брони.

## Вопросы для самопроверки

- Почему Go `sync.Mutex` не решит двойное бронирование при двух экземплярах приложения?
- Почему сначала нужно взять блокировку, а затем проверить время?
- Чем `clock_timestamp()` отличается от времени начала транзакции?
- Почему TTL должен храниться в базе, а не только в `time.Timer`?
- Зачем нужны и блокировка строки, и уникальный индекс?
- Что произойдёт, если база сохранила бронь, а клиент не получил ответ?
- Почему повтор старого ключа после отмены не должен создавать новую бронь?
- Почему роль проверяется из базы, а не принимается из тела регистрации?
- Как убедиться, что клиент не подтвердит чужую бронь, подставив ID?
- Как влияет `SKIP LOCKED` на уборку просроченных броней?

## Демонстрация для GitHub

В README своего репозитория добавь собственные скриншоты интерфейса и короткое видео: регистрация → выбор места → бронь → подтверждение. Покажи вывод конкурентного теста. Объясни три решения: блокировки, идемпотентность, истечение срока.

Перед загрузкой выполни `git status`: `.env` с паролями не должен попадать в коммит. `go.mod`, `go.sum`, `.env.example`, тесты и исходники должны попасть.

## Следующие самостоятельные улучшения

1. **История статусов.** Таблица `booking_events`; запись статуса и истории в одной транзакции.
2. **Фильтры мероприятий.** Поиск по названию и дате, корректная пагинация.
3. **Обновления через SSE.** Доставлять изменения мест без опроса каждые пять секунд.
4. **Несколько мест в одной брони.** Брать блокировки всех мест в одном порядке, сохранять всё или ничего.
5. **Реальные уведомления.** Сначала спроектировать outbox и обработку повторов, затем добавлять отправку почты.

Начни с истории статусов: это небольшой следующий шаг, который можно сделать самому, не меняя весь проект.
